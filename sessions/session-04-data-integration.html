6  Session 4 — Data Integration

Five ways to combine sources · concat · merge · the four join types · what goes wrong

Note

This chapter is about combining data that arrives in more than one piece.

Assumed knowledge: Sessions 2 and 3 — loading a DataFrame, filtering, and cleaning text columns. The text-cleaning part matters here: you cannot join on a key you have not cleaned.

The one idea to take away: every join can silently lose rows or silently multiply them. Print the row count before and after. Every time.

6.1 🎯 Learning outcomes

By the end of this chapter you can:

  1. Describe the five approaches to data integration and pick one for a situation.
  2. Stack tables with concat and link tables with merge.
  3. Use all four join types and predict how many rows each returns.
  4. Detect a join that lost rows and a join that multiplied them.
  5. Fix the three things that break a join: mismatched keys, different names for the same thing, and duplicate keys.

7 Part A — Five ways to integrate

7.1 1. Why data is never in one place

Data integration is combining data from several sources into one view you can analyse.

It exists because organisations do not store data for the convenience of analysts. Sales sit in the sales system, support tickets in the helpdesk, web visits in the analytics tool. Each was built for its own job. The question “do customers who contact support buy less?” touches all three, and no single system can answer it.

Tip🧠 Analogy — the wedding guest list

One partner keeps family names in a notebook; the other keeps friends in a spreadsheet. Neither list is wrong. But you cannot count chairs, order food or print place cards until they are one list.

The painful part is not the copying — it is that “R. Sharma” and “Raj Sharma” might be the same person, or might be two people. That question is the whole of data integration.

7.2 2. The five approaches

There are five ways to combine sources. They differ in one thing: how much data you copy, and who does the translating.

Approach What happens Data is copied? Good Bad
Physical (data warehouse) copy everything into one central database on a schedule yes fast queries; one place to look data is as old as the last copy; expensive
Virtual (federation) leave data where it is; a layer queries each source live when asked no always current; nothing to store slow; breaks when any source is down
Application-based each application translates and pushes its own data to the others partly no central system needed every app must know about every other; n apps means many links
Middleware one translation layer sits between sources and converts formats partly apps stay simple; one place to fix the middleware becomes a single point of failure
Manual a person exports CSVs and combines them by hand yes needs nothing; works today slow, unrepeatable, and error-prone

7.2.1 How to choose

Warning⚠️ Manual integration is where most reporting errors come from

Copying and pasting between spreadsheets leaves no record of what was done, cannot be repeated identically, and fails silently when a column shifts by one. If a manual integration is going to happen more than twice, write the code instead.

8 Part B — Doing it in pandas

8.1 3. Stacking versus linking

There are two different operations, and mixing them up is the most common beginner error.

Operation Question it answers Function
Stacking “here are more rows of the same thing” pd.concat
Linking “here is extra information about the same things” pd.merge

Two months of sales → stack. Customers and their orders → link.

8.1.1 Demo 1 — stacking with concat

import pandas as pd

jan = pd.read_csv("datasets/sales_jan.csv")
feb = pd.read_csv("datasets/sales_feb.csv")
print("January:"); print(jan)
print("\nFebruary:"); print(feb)
print()

stacked = pd.concat([jan, feb], ignore_index=True)
print(stacked)
print(f"\n{len(jan)} + {len(feb)} = {len(stacked)} rows. Columns unchanged: {list(stacked.columns)}")
January:
         date  amount
0  2024-01-05     250
1  2024-01-19      90

February:
         date  amount
0  2024-02-02     410
1  2024-02-27     130

         date  amount
0  2024-01-05     250
1  2024-01-19      90
2  2024-02-02     410
3  2024-02-27     130

2 + 2 = 4 rows. Columns unchanged: ['date', 'amount']

ignore_index=True renumbers the rows. Without it you get row labels 0, 1, 0, 1 — two rows labelled 0, which causes confusing errors later.

Warning⚠️ concat lines columns up by name

If one month’s file calls the column amount and the other calls it Amount, concat does not complain. It creates both columns and fills each with blanks where the other was used. Check .columns on both tables before stacking.

mismatched = pd.read_csv("datasets/sales_mar.csv")   # this file spells it "Amount"
print("March, as it arrived:"); print(mismatched)
oops = pd.concat([jan, mismatched], ignore_index=True)
print()
print(oops)
print("\nTwo amount columns, both half empty — and no error was raised.")
March, as it arrived:
         date  Amount
0  2024-03-01     500

         date  amount  Amount
0  2024-01-05   250.0     NaN
1  2024-01-19    90.0     NaN
2  2024-03-01     NaN   500.0

Two amount columns, both half empty — and no error was raised.

8.1.2 Demo 2 — the fix: rename first, then stack all three

Checking .columns found the problem. Fixing it is one line — rename the odd column out to match the others — and then all three months stack cleanly.

mar_fixed = mismatched.rename(columns={"Amount": "amount"})
all_three = pd.concat([jan, feb, mar_fixed], ignore_index=True)
print(all_three)
print(f"\n{len(jan)}+{len(feb)}+{len(mar_fixed)} = {len(all_three)} rows, "
      f"one column: {list(all_three.columns)}")
         date  amount
0  2024-01-05     250
1  2024-01-19      90
2  2024-02-02     410
3  2024-02-27     130
4  2024-03-01     500

2+2+1 = 5 rows, one column: ['date', 'amount']

One rename and the three-way stack behaves exactly like the two-way one did — a single amount column, no blanks, no silent duplication. The fix is always this cheap once you have actually looked at .columns.

8.2 4. Linking tables with merge

merge joins two tables using a shared column called the key. The key is usually an ID.

8.2.1 Demo 2 — a first merge

import pandas as pd

customers = pd.read_csv("datasets/customers.csv")
purchases = pd.read_csv("datasets/purchases.csv")

print("customers:"); print(customers)
print("\npurchases:"); print(purchases)

joined = pd.merge(customers, purchases, on="user_id", how="inner")
print("\nInner join:"); print(joined)
print(f"\ncustomers {len(customers)} rows + purchases {len(purchases)} rows → {len(joined)} rows")
customers:
   user_id   name    city
0        1  Alice  Mumbai
1        2    Bob   Delhi
2        3   Chan  Mumbai
3        4   Devi    Pune

purchases:
   purchase_id  user_id  amount
0          101        1   250.0
1          102        1   120.0
2          103        3    75.5
3          104        5   300.0

Inner join:
   user_id   name    city  purchase_id  amount
0        1  Alice  Mumbai          101   250.0
1        1  Alice  Mumbai          102   120.0
2        3   Chan  Mumbai          103    75.5

customers 4 rows + purchases 4 rows → 3 rows

Read that row count carefully. Four and four made three. Bob and Devi vanished (no purchases), user 5 vanished (not a known customer), and Alice appears twice (two purchases). This is normal, and it is why you check.

8.2.2 Demo 3 — seeing exactly which rows matched

Counting rows before and after tells you that something changed. indicator=True adds a column telling you which side every row came from, so you never have to guess.

tagged = pd.merge(customers, purchases, on="user_id", how="outer", indicator=True)
print(tagged[["user_id", "name", "purchase_id", "_merge"]])
print("\nCount by origin:")
print(tagged["_merge"].value_counts())
   user_id   name  purchase_id      _merge
0        1  Alice        101.0        both
1        1  Alice        102.0        both
2        2    Bob          NaN   left_only
3        3   Chan        103.0        both
4        4   Devi          NaN   left_only
5        5    NaN        104.0  right_only

Count by origin:
_merge
both          3
left_only     2
right_only    1
Name: count, dtype: int64

both means the row matched on both sides. left_only is Bob and Devi — customers with no purchase. right_only is the purchase from user 5, who is not a known customer at all. This is the same information the row count gave you, broken down by exactly who is missing — and it scales to joins far too big to eyeball.

8.3 5. The four join types

The join type answers one question: which rows do you keep when there is no match?

Type Keeps Use when
inner only rows matching in both you need complete records
left all left rows; blanks where no match the left table is your population
right all right rows rare — usually a left with the tables swapped
outer everything from both you are looking for what does not match

8.3.1 Demo 3 — all four, on the same two tables

for how in ["inner", "left", "right", "outer"]:
    result = pd.merge(customers, purchases, on="user_id", how=how)
    names = result["name"].fillna("(unknown)").tolist()
    print(f"{how:>6}: {len(result)} rows — {names}")
 inner: 3 rows — ['Alice', 'Alice', 'Chan']
  left: 5 rows — ['Alice', 'Alice', 'Bob', 'Chan', 'Devi']
 right: 4 rows — ['Alice', 'Alice', 'Chan', '(unknown)']
 outer: 6 rows — ['Alice', 'Alice', 'Bob', 'Chan', 'Devi', '(unknown)']

Now read what each one is for:

print("LEFT — every customer, whether or not they bought anything:")
left = pd.merge(customers, purchases, on="user_id", how="left")
print(left[["name", "city", "amount"]])

print("\nWho has never bought anything? The rows where amount is blank:")
print(left[left["amount"].isna()]["name"].tolist())

print("\nOUTER — everything, including the purchase by an unknown user 5:")
outer = pd.merge(customers, purchases, on="user_id", how="outer")
print(outer[outer["name"].isna()][["user_id", "purchase_id", "amount"]])
LEFT — every customer, whether or not they bought anything:
    name    city  amount
0  Alice  Mumbai   250.0
1  Alice  Mumbai   120.0
2    Bob   Delhi     NaN
3   Chan  Mumbai    75.5
4   Devi    Pune     NaN

Who has never bought anything? The rows where amount is blank:
['Bob', 'Devi']

OUTER — everything, including the purchase by an unknown user 5:
   user_id  purchase_id  amount
5        5        104.0   300.0

The left join answered a business question the inner join could not: which customers have never purchased. An inner join deletes exactly those people.

Tip🧠 Analogy — the class register

inner — students who are on the register and sat the exam. left — the whole register; those who missed the exam show a blank mark. outer — the register plus any exam papers from people who are not on it.

The blanks are not a nuisance. They are usually the finding.

8.3.2 Demo 4 — what if both sides repeat the key?

Every example so far had a repeated key on one side only (Alice, twice, in purchases). What if customers also had a repeated key?

# Duplicate Alice's row once, on purpose, so user_id 1 now appears twice on the LEFT too.
customers_with_dup = pd.concat([customers, customers[customers["user_id"] == 1]],
                                ignore_index=True)
print(f"customers: {len(customers)} rows -> customers_with_dup: {len(customers_with_dup)} rows")

many_to_many = pd.merge(customers_with_dup, purchases, on="user_id", how="inner")
print(f"\n{len(customers_with_dup)} x {len(purchases)} -> {len(many_to_many)} rows")
print(many_to_many[["user_id", "name", "purchase_id", "amount"]])
customers: 4 rows -> customers_with_dup: 5 rows

5 x 4 -> 5 rows
   user_id   name  purchase_id  amount
0        1  Alice          101   250.0
1        1  Alice          102   120.0
2        1  Alice          101   250.0
3        3   Chan          103    75.5
4        1  Alice          102   120.0

Alice’s two customer rows each matched against her two purchase rows — 2 × 2 = 4 rows, where a clean key on both sides would have given 2. This is called a many-to-many join, and the row count is not additive, it is multiplicative: duplicate a key on both sides and the damage compounds instead of just adding up.

8.4 6. Aggregate, then join

When one side has many rows per key, joining directly multiplies rows. Usually you want a summary instead.

8.4.1 Demo 4 — one row per customer

# Wrong for most purposes: Alice appears twice, so any count of customers is now wrong.
naive = pd.merge(customers, purchases, on="user_id", how="left")
print(f"Naive join: {len(naive)} rows for {len(customers)} customers")

# Right: summarise the many side first, then join one-to-one.
per_customer = purchases.groupby("user_id").agg(
    n_purchases=("purchase_id", "count"),
    total_spent=("amount", "sum"),
).reset_index()

summary = pd.merge(customers, per_customer, on="user_id", how="left")
summary["n_purchases"] = summary["n_purchases"].fillna(0).astype(int)
summary["total_spent"] = summary["total_spent"].fillna(0)

print(f"\nAggregate-then-join: {len(summary)} rows for {len(customers)} customers")
print(summary)
Naive join: 5 rows for 4 customers

Aggregate-then-join: 4 rows for 4 customers
   user_id   name    city  n_purchases  total_spent
0        1  Alice  Mumbai            2        370.0
1        2    Bob   Delhi            0          0.0
2        3   Chan  Mumbai            1         75.5
3        4   Devi    Pune            0          0.0

One row per customer, every customer present, spending totalled. This aggregate-then-join pattern is the one you will use most often in real work.

8.4.2 Demo 5 — what if you forget .reset_index()?

The aggregate above ended with .reset_index(). Skip it, and user_id stops being a column — it becomes the table’s index instead. Does the merge still work?

per_customer_noreset = purchases.groupby("user_id").agg(total_spent=("amount", "sum"))
print("Columns:", list(per_customer_noreset.columns))
print("Index name:", per_customer_noreset.index.name)

still_works = pd.merge(customers, per_customer_noreset, on="user_id", how="left")
print("\nMerged anyway:")
print(still_works)
Columns: ['total_spent']
Index name: user_id

Merged anyway:
   user_id   name    city  total_spent
0        1  Alice  Mumbai        370.0
1        2    Bob   Delhi          NaN
2        3   Chan  Mumbai         75.5
3        4   Devi    Pune          NaN

It works — pandas will match on="user_id" against an index name, not just a column name. But look at print("Columns:", ...) above: user_id is nowhere in it. Any other code that expects per_customer_noreset["user_id"] to exist — a filter, another merge, a plot — breaks, even though this particular merge did not. .reset_index() costs one line and removes the surprise.

9 Part C — What goes wrong

9.1 7. The three failures

9.1.1 Failure 1 — the key does not match

The most common cause of “the join returned nothing”. The keys look identical to a human and differ to a computer.

left_tbl  = pd.read_csv("datasets/subscribers_plan.csv")
right_tbl = pd.read_csv("datasets/subscribers_spend.csv")
print("The two files, side by side — the emails LOOK identical:")
print(left_tbl.to_dict("records"))
print(right_tbl.to_dict("records"))

print("\nJoining as-is:")
print(pd.merge(left_tbl, right_tbl, on="email", how="inner"))
print("→ 0 rows. One key has capitals, the other has a trailing space.\n")

for t in (left_tbl, right_tbl):
    t["email"] = t["email"].str.strip().str.lower()

print("After cleaning the key:")
print(pd.merge(left_tbl, right_tbl, on="email", how="inner"))
The two files, side by side — the emails LOOK identical:
[{'email': 'ASHA@mail.com', 'plan': 'gold'}, {'email': 'brij@mail.com ', 'plan': 'silver'}]
[{'email': 'asha@mail.com', 'spend': 900}, {'email': 'brij@mail.com', 'spend': 400}]

Joining as-is:
Empty DataFrame
Columns: [email, plan, spend]
Index: []
→ 0 rows. One key has capitals, the other has a trailing space.

After cleaning the key:
           email    plan  spend
0  asha@mail.com    gold    900
1  brij@mail.com  silver    400

Clean the key before you join. Trim spaces, fix the case, standardise the format. This is why Session 3 comes before this chapter.

9.1.2 Failure 2 — the same thing, different column names

orders = pd.read_csv("datasets/orders_by_ref.csv")   # this file calls the key cust_ref

merged = pd.merge(customers, orders, left_on="user_id", right_on="cust_ref", how="inner")
print(merged[["user_id", "name", "cust_ref", "total"]])
print("\n`left_on` and `right_on` join columns that mean the same thing but are named differently.")
   user_id   name  cust_ref  total
0        1  Alice         1    500
1        2    Bob         2    250

`left_on` and `right_on` join columns that mean the same thing but are named differently.

9.1.3 Failure 3 — duplicate keys multiply rows

This is the dangerous one, because nothing fails. The code runs, the model trains, the numbers look plausible, and they are wrong.

# A dirty reference table: 'Mumbai' is listed twice by mistake.
regions = pd.read_csv("datasets/regions_dirty.csv")
print(regions)
print()

blown_up = pd.merge(customers, regions, on="city", how="left")
print(f"customers: {len(customers)} rows  →  after joining regions: {len(blown_up)} rows")
print(blown_up[["user_id", "name", "city", "region"]])
print("\nAlice and Chan each appear twice. Every total computed from this table is now")
print("double-counted for Mumbai — and nothing raised an error.")

# The fix: make sure the lookup table has one row per key before joining.
regions_clean = regions.drop_duplicates(subset="city")
fixed = pd.merge(customers, regions_clean, on="city", how="left")
print(f"\nAfter de-duplicating the lookup table: {len(fixed)} rows")
     city region
0  Mumbai   West
1   Delhi  North
2    Pune   West
3  Mumbai   West

customers: 4 rows  →  after joining regions: 6 rows
   user_id   name    city region
0        1  Alice  Mumbai   West
1        1  Alice  Mumbai   West
2        2    Bob   Delhi  North
3        3   Chan  Mumbai   West
4        3   Chan  Mumbai   West
5        4   Devi    Pune   West

9.2 8. The check that catches all three

One helper function, used after every join, catches every failure in this chapter.

def check_join(left, right, result, name="join"):
    """Report what a join did to the row count, and whether keys went unmatched."""
    print(f"{name}: left {len(left)} × right {len(right)} → result {len(result)}")
    if len(result) > len(left):
        print(f"  ⚠ GREW by {len(result)-len(left)} rows — the right table has duplicate keys")
    elif len(result) < len(left):
        print(f"  ⚠ SHRANK by {len(left)-len(result)} rows — some left keys had no match")
    else:
        print("  ✓ one row in, one row out")
    blanks = result.isna().sum()
    if blanks.any():
        print(f"  unmatched values appear as blanks in: {blanks[blanks>0].to_dict()}")

check_join(customers, regions, blown_up, "customers + dirty regions")
print()
check_join(customers, regions_clean, fixed, "customers + clean regions")
print()
check_join(customers, purchases, pd.merge(customers, purchases, on="user_id"), "customers + purchases (inner)")
customers + dirty regions: left 4 × right 4 → result 6
  ⚠ GREW by 2 rows — the right table has duplicate keys

customers + clean regions: left 4 × right 3 → result 4
  ✓ one row in, one row out

customers + purchases (inner): left 4 × right 4 → result 3
  ⚠ SHRANK by 1 rows — some left keys had no match
Warning⚠️ A join that changes the row count is a claim, not an accident

A shrinking join says “these records had no match”. A growing join says “one of these keys is not unique”. Both may be fine — but you should be able to say which, and why, before you use the result.

11 ❓ MCQs

Q1. A dashboard must show live warehouse stock, and stock changes every few seconds. Which approach?

    1. Physical integration into a nightly warehouse.
    1. Virtual integration, querying the stock system directly.
    1. Manual integration.

Q2. Twelve internal systems each need data from the other eleven, and every team is writing its own converter. Which approach fixes this?

    1. Manual integration.
    1. Virtual integration.
    1. Middleware — one translation layer instead of many pairwise converters.

Q3. You have 1,000 customers and join a city → region lookup. You get 1,043 rows. What happened?

    1. 43 customers were added.
    1. The lookup table has duplicate city entries, so some customers matched twice.
    1. The join type was wrong.

Q4. You want every product listed in a sales report, including those that sold nothing this month. Which join?

    1. inner, from sales to products.
    1. left, from products to sales.
    1. right, from products to sales.

Q5. A merge on email returns 0 rows even though both tables clearly contain the same people. Most likely cause?

    1. Pandas is broken.
    1. The keys differ in case or whitespace.
    1. The tables are too large.
NoteAnswers

A1 — (b). A nightly copy would show yesterday’s stock, which for this question is worse than useless. Virtual integration trades speed for freshness, and freshness is what this dashboard is for.

A2 — (c). With 12 systems talking directly, you can end up maintaining dozens of converters. Middleware means each system talks to one thing.

A3 — (b). Demo in Failure 3. Every total computed afterwards is inflated for the duplicated cities.

A4 — (b). Start from the table whose rows you want to keep all of. Products with no sales come through with blank sales figures — which is exactly the answer you wanted.

A5 — (b). Failure 1. "ASHA@mail.com" and "asha@mail.com" are different strings.
