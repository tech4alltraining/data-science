14  Session 12 — Model Saving and Deployment

Saving the pipeline · Inference · Offline vs online · Streamlit · What breaks after launch

Note

This chapter puts a model somewhere other people can use it.

Assumed knowledge: Session 5 — pipelines. Session 9 — training a regression. Session 11 — evaluating one honestly.

The one idea to take away: save the whole pipeline, never the model alone. A model saved without its scaler and encoder will accept raw input and return confident nonsense, and nothing will raise an error.

14.1 🎯 Learning outcomes

By the end of this chapter you can:

  1. Save and reload a trained pipeline with joblib.
  2. Explain why saving the estimator alone produces silent, wrong predictions.
  3. Write a predict_one() function that takes raw user input.
  4. Choose between offline (batch) and online (live) deployment.
  5. Write and run a Streamlit application around a saved model.
  6. Name three things that break a deployed model after launch.

15 Part A — Saving

15.1 1. Why a trained model has to be saved

Training happens once; predicting happens thousands of times. Retraining a model every time somebody asks a question would be slow, expensive, and would give slightly different answers each run.

So the trained model is written to a file. That file contains the learned numbers — coefficients, tree splits, the scaler’s mean — and can be loaded in milliseconds.

Tip🧠 Analogy — the recipe and the cooking

Working out a recipe takes weeks of experimenting. Cooking from it takes twenty minutes.

Training is developing the recipe. Saving is writing it down. Prediction is cooking. You do not redevelop the recipe every time somebody orders dinner.

15.2 2. Save the pipeline, not the model

This is the mistake that costs the most and announces itself the least.

A trained LinearRegression knows its coefficients. It does not know that its inputs were scaled before training. Feed it raw, unscaled numbers and it will apply coefficients meant for scaled ones — and return a number, confidently, with no error.

15.2.1 Demo 1 — the silent failure, measured

import numpy as np, pandas as pd
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LinearRegression
from sklearn.pipeline import Pipeline
from sklearn.model_selection import train_test_split

homes = pd.read_csv("datasets/house_prices_simple.csv")
print(f"{len(homes)} houses on file: {list(homes.columns)}\n")

X = homes[["area_sqft", "age_years"]]
y = homes["price"]
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=.2, random_state=0)

# Train with scaling, as Session 5 taught.
scaler = StandardScaler().fit(X_train)
model = LinearRegression().fit(scaler.transform(X_train), y_train)

new_house = pd.DataFrame([{"area_sqft": 1500, "age_years": 5}])

right = model.predict(scaler.transform(new_house))[0]     # scaled, as trained
wrong = model.predict(new_house)[0]                       # raw — the bug

print(f"Correct  (scaled input) : ₹{right:>15,.0f}")
print(f"Bug      (raw input)    : ₹{wrong:>15,.0f}")
print(f"\nNo error was raised. The wrong answer is off by ₹{abs(right-wrong):,.0f}.")
500 houses on file: ['area_sqft', 'age_years', 'price']

Correct  (scaled input) : ₹      4,994,176
Bug      (raw input)    : ₹  1,694,069,949

No error was raised. The wrong answer is off by ₹1,689,075,773.

Both lines ran without complaint. In a web app, the second would be shown to a user as a house valuation.

15.2.2 Demo 2 — the fix: one object that carries everything

from sklearn.pipeline import Pipeline

pipeline = Pipeline([
    ("scale", StandardScaler()),
    ("model", LinearRegression()),
]).fit(X_train, y_train)

print(f"Pipeline on raw input   : ₹{pipeline.predict(new_house)[0]:>15,.0f}")
print(f"Correct answer from above: ₹{right:>15,.0f}")
print("\nThe pipeline takes RAW input and scales it internally. There is no way")
print("to forget the scaler, because the scaler is inside the thing you saved.")
Pipeline on raw input   : ₹      4,994,176
Correct answer from above: ₹      4,994,176

The pipeline takes RAW input and scales it internally. There is no way
to forget the scaler, because the scaler is inside the thing you saved.

15.3 3. Saving and loading

joblib writes a fitted Python object to a file and reads it back. It is preferred over pickle for scikit-learn because it stores large numeric arrays more efficiently.

15.3.1 Demo 3 — a full save-and-reload round trip

import joblib, tempfile, os
import numpy as np

folder = tempfile.mkdtemp()
path = os.path.join(folder, "house_price_pipeline.joblib")

joblib.dump(pipeline, path)
print(f"saved to {os.path.basename(path)}  ({os.path.getsize(path):,} bytes)")

loaded = joblib.load(path)
print(f"loaded back: {type(loaded).__name__} with steps {[n for n, _ in loaded.steps]}")

before = pipeline.predict(X_test)
after   = loaded.predict(X_test)
print(f"\npredictions identical after reload: {np.allclose(before, after)}")
print(f"largest difference: {np.abs(before - after).max():.10f}")
saved to house_price_pipeline.joblib  (1,361 bytes)
loaded back: Pipeline with steps ['scale', 'model']

predictions identical after reload: True
largest difference: 0.0000000000

15.3.2 Demo 4 — save everything needed to reproduce the model

import joblib, sklearn, os, json
from datetime import date
from sklearn.metrics import mean_absolute_error, r2_score

bundle = {
    "pipeline": pipeline,
    "feature_names": list(X.columns),           # so the app builds rows in the right order
    "target": "price",
    "trained_on": str(date.today()),
    "n_training_rows": len(X_train),
    "sklearn_version": sklearn.__version__,
    "test_mae": float(mean_absolute_error(y_test, pipeline.predict(X_test))),
    "test_r2": float(r2_score(y_test, pipeline.predict(X_test))),
}

bundle_path = os.path.join(folder, "model_bundle.joblib")
joblib.dump(bundle, bundle_path)

back = joblib.load(bundle_path)
print(json.dumps({k: v for k, v in back.items() if k != "pipeline"}, indent=2))

Everything except the pipeline itself is metadata, and every field earns its place:

Field Answers
feature_names what order do the columns go in?
sklearn_version why does this behave differently now?
test_mae, test_r2 is the live model still as good as when we shipped it?
trained_on how stale is this?
Warning⚠️ A saved model is tied to its library version

A pipeline saved under scikit-learn 1.3 and loaded under 1.5 may warn, may behave differently, or may refuse to load. Pin your versions in requirements.txt and record the version in the bundle so the mismatch is diagnosable rather than mysterious.

print("requirements.txt should pin exactly what trained the model, for example:")
print(f"  scikit-learn=={sklearn.__version__}")
print(f"  pandas=={pd.__version__}")
print(f"  numpy=={np.__version__}")

16 Part B — Serving

16.1 4. One inference function

Write one function that turns raw user input into a prediction, and use it everywhere — the notebook, the app, the batch job, the tests. If the app builds its input rows differently from the notebook, you have two models.

16.1.1 Demo 5 — the plain inference call

import pandas as pd, joblib

bundle = joblib.load(bundle_path)
row = pd.DataFrame([{"area_sqft": 1500, "age_years": 5}])
price = bundle["pipeline"].predict(row[bundle["feature_names"]])[0]
print(f"1500 sqft, 5 years old → ₹{price:,.0f}")
1500 sqft, 5 years old → ₹4,994,176

That is genuinely all a prediction is: load the bundle, build one row, call predict. But typed out again in the notebook, again in the app and again in a test, it will drift — one copy will forget to reorder the columns, another will forget to validate. Demo 6 wraps this exact call in one function so there is only one copy to get right.

16.1.2 Demo 6 — predict_one, with input validation

import pandas as pd, joblib

def load_model(path):
    b = joblib.load(path)
    return b["pipeline"], b["feature_names"]

def predict_price(area_sqft, age_years, model_path=bundle_path):
    """Turn raw user input into a price. Validates before predicting."""
    if not 200 <= area_sqft <= 10_000:
        raise ValueError(f"area_sqft {area_sqft} is outside the sensible range 200–10,000")
    if not 0 <= age_years <= 120:
        raise ValueError(f"age_years {age_years} is outside the sensible range 0–120")

    pipe, features = load_model(model_path)
    row = pd.DataFrame([{"area_sqft": area_sqft, "age_years": age_years}])[features]
    return float(pipe.predict(row)[0])

for area, age in [(800, 2), (1500, 5), (2400, 20)]:
    print(f"{area:>5} sqft, {age:>2} years old → ₹{predict_price(area, age):>12,.0f}")

try:
    predict_price(-50, 5)
except ValueError as e:
    print(f"\nRejected bad input: {e}")
  800 sqft,  2 years old → ₹   2,878,291
 1500 sqft,  5 years old → ₹   4,994,176
 2400 sqft, 20 years old → ₹   7,199,992

Rejected bad input: area_sqft -50 is outside the sensible range 200–10,000
Important🔓 Validate at the door

A model will happily predict a price for a house of −50 square feet. The model is not where you catch nonsense — the input layer is. Every deployed model needs a range check in front of it, because users type things.

16.2 5. Offline and online deployment

There are two ways to deliver predictions, and the choice follows from when the answer is needed.

Offline (batch) Online (live)
When it runs on a schedule — nightly, weekly the moment someone asks
Input a whole file of rows one row
Output a table of predictions one answer
Delivered as a CSV, a database table, a dashboard a web app or an API
Needs a server running? no — a scheduled job yes, always on
Cost low higher
Good for churn scores, restock lists, risk ratings loan decisions, fraud checks, search

Most projects should start offline. If a nightly file of predictions solves the problem, you have avoided servers, uptime and latency entirely.

16.2.1 Demo 7 — offline scoring, which is often the whole product

import pandas as pd, joblib, os

# A batch job: read the properties awaiting valuation, score them, write the file, stop.

16.2.2 Demo 8 — online scoring, one request at a time

import time, joblib

pipe, features = load_model(bundle_path)          # load ONCE, not per request

def handle_request(payload: dict) -> dict:
    """What a web endpoint does for a single incoming request."""
    start = time.perf_counter()
    row = pd.DataFrame([payload])[features]
    price = float(pipe.predict(row)[0])
    return {
        "estimated_price": round(price, -3),
        "confidence_note": "typical error ±₹{:,.0f}".format(joblib.load(bundle_path)["test_mae"]),
        "latency_ms": round((time.perf_counter() - start) * 1000, 2),
    }

for payload in [{"area_sqft": 1500, "age_years": 5}, {"area_sqft": 2400, "age_years": 20}]:
    print(payload, "→", handle_request(payload))
{'area_sqft': 1500, 'age_years': 5} → {'estimated_price': 4994000.0, 'confidence_note': 'typical error ±₹169,824', 'latency_ms': 1.57}
{'area_sqft': 2400, 'age_years': 20} → {'estimated_price': 7200000.0, 'confidence_note': 'typical error ±₹169,824', 'latency_ms': 1.26}

Note where the model is loaded. Loading it inside the request function would reread the file on every call. Loading it once, when the process starts, is the difference between a page that responds instantly and one that does not.

17 Part C — Streamlit

17.1 6. What Streamlit does

Streamlit turns a Python script into a web page. There is no HTML, no JavaScript and no web framework to learn: you write st.slider(...) and a slider appears.

Every Streamlit app is the same four steps:

Step Code
1. Load the model once @st.cache_resource + joblib.load
2. Collect input from widgets st.slider, st.number_input, st.selectbox
3. Predict pipeline.predict(row)
4. Show the answer st.metric, st.write

17.2 7. The app

The code below is a complete, working application. It is shown rather than run, because a Streamlit app needs a web server — the cells in this book run in a notebook kernel. Save it as app.py and run streamlit run app.py.

# app.py — a complete house price estimator
import streamlit as st
import pandas as pd
import joblib

st.set_page_config(page_title="House price estimator", page_icon="🏠")

# --- STEP 1: load the model ONCE, not on every interaction -----------------
@st.cache_resource
def load_bundle():
    return joblib.load("model_bundle.joblib")

bundle = load_bundle()
pipeline = bundle["pipeline"]
features = bundle["feature_names"]

# --- STEP 2: collect input -------------------------------------------------
st.title("🏠 House price estimator")
st.caption(f"Model trained {bundle['trained_on']} on {bundle['n_training_rows']:,} properties")

col1, col2 = st.columns(2)
with col1:
    area = st.slider("Floor area (sq ft)", 400, 3000, 1200, step=50)
with col2:
    age = st.slider("Age of property (years)", 0, 40, 5)

# --- STEP 3: predict -------------------------------------------------------
row = pd.DataFrame([{"area_sqft": area, "age_years": age}])[features]
price = float(pipeline.predict(row)[0])

# --- STEP 4: show the answer, with its uncertainty -------------------------
st.metric("Estimated price", f"₹{price:,.0f}")
st.caption(f"Typical error on unseen properties: ±₹{bundle['test_mae']:,.0f}")

with st.expander("How reliable is this?"):
    st.write(f"""
    - Test R²: **{bundle['test_r2']:.2f}** — the share of price variation the model explains
    - Trained on properties between 400 and 3,000 sq ft. Estimates outside that
      range are extrapolation and should not be relied on.
    - This is a statistical estimate, not a valuation.
    """)
Warning⚠️ @st.cache_resource is not optional

Without it, Streamlit reruns the entire script every time a slider moves — including joblib.load. On a large model that is a visible freeze on every interaction. @st.cache_resource loads it once and keeps it.

17.2.1 Demo 9 — the app’s logic, tested without a browser

17.2.2 Demo 10 — sanity checks the app should pass

bigger_costs_more = app_logic(2000, 5) > app_logic(1000, 5)
older_costs_less = app_logic(1500, 30) < app_logic(1500, 2)

print(f"bigger house costs more     : {bigger_costs_more}")

older house costs less      : True
test MAE quoted to the user : ₹169,824

These are checks a test suite would run automatically before every deploy — not because anyone expects them to fail, but because a silent regression (Demo 1’s bug, for instance) would fail exactly one of them, immediately, instead of waiting for a user to notice a nonsensical price.

17.3 8. Publishing it

Streamlit Community Cloud hosts small apps free, straight from a GitHub repository.

Your repository needs Why
app.py the application
model_bundle.joblib the trained pipeline, committed
requirements.txt with versions pinned
README.md what it does and what it must not be used for

Then: push to GitHub → connect the repository at share.streamlit.io → choose app.py → deploy.

Warning⚠️ Never commit secrets

API keys, database passwords and connection strings must not be in the repository, and must not be in the model bundle. Streamlit provides st.secrets for this. A key pushed to GitHub is compromised even if you delete it afterwards — the history keeps it.

18 Part D — After launch

18.1 9. What breaks

A deployed model degrades even when nobody touches the code, because the world it learned from carries on changing.

Problem What happens How you notice
Data drift inputs shift — house sizes, customer ages monitor input distributions
Concept drift the relationship shifts — a market crash monitor live accuracy
Schema change an upstream column is renamed or reformatted the app crashes, or worse, silently misreads
Version drift the library is upgraded under the model pin versions; record them
Extrapolation users enter values outside the training range validate inputs

18.1.1 Demo 11 — detecting drift by watching the inputs

import numpy as np, pandas as pd

training_areas = X_train["area_sqft"]

# What the live service actually received, month by month.
incoming = pd.read_csv("datasets/incoming_requests.csv")
months = {m: g["area_sqft"].values for m, g in incoming.groupby("month")}

print(f"training data: mean {training_areas.mean():,.0f}, "
      f"Q1 {training_areas.quantile(.25):,.0f}, Q3 {training_areas.quantile(.75):,.0f}\n")

for name, seen in months.items():
    shift = (seen.mean() - training_areas.mean()) / training_areas.std()
    outside = ((seen < training_areas.min()) | (seen > training_areas.max())).mean()
    flag = "  ⚠ DRIFT — retrain" if abs(shift) > 0.5 else ""
    print(f"{name}: mean {seen.mean():>7,.0f}   shift {shift:+.2f} std   "
          f"{outside:>5.1%} outside training range{flag}")
training data: mean 1,184, Q1 953, Q3 1,418

Month 1: mean   1,189   shift +0.01 std    0.7% outside training range
Month 4: mean   1,259   shift +0.21 std    0.7% outside training range
Month 8: mean   1,695   shift +1.45 std    2.0% outside training range  ⚠ DRIFT — retrain

No accuracy figure was needed. Watching the inputs catches drift before the predictions have visibly gone wrong — and long before anybody complains.

18.1.2 Demo 12 — the deployment checklist, as code

import joblib, os

def has_preprocessing_step(pipeline):
    """True if any step name looks like scaling, encoding or imputation."""
    keywords = ("scal", "prep", "impute")
    step_names = [name for name, _ in pipeline.steps]
    return any(keyword in name for name in step_names for keyword in keywords)

def preflight(bundle_path):
    """Checks to run before any model goes live."""
    b = joblib.load(bundle_path)
    checks = {
        "pipeline saved (not a bare model)": hasattr(b["pipeline"], "steps"),
        "preprocessing inside the pipeline": has_preprocessing_step(b["pipeline"]),
        "feature order recorded":            bool(b.get("feature_names")),
        "library version recorded":          bool(b.get("sklearn_version")),
        "test score recorded":               b.get("test_r2") is not None,
        "training date recorded":            bool(b.get("trained_on")),
        "file is loadable":                  os.path.getsize(bundle_path) > 0,
    }
    for name, ok in checks.items():
        print(f"  {'✓' if ok else '✗'}  {name}")
    return all(checks.values())

print("PRE-FLIGHT CHECKS")
print(f"\nready to deploy: {preflight(bundle_path)}")
PRE-FLIGHT CHECKS
  ✓  pipeline saved (not a bare model)
  ✓  preprocessing inside the pipeline
  ✓  feature order recorded
  ✓  library version recorded
  ✓  test score recorded
  ✓  training date recorded
  ✓  file is loadable

ready to deploy: True

def predict_checked(area, age):
    warnings = [f"{c}={v} is outside the training range {bounds[c]}"
                for c, v in [("area_sqft", area), ("age_years", age)]
                if not bounds[c][0] <= v <= bounds[c][1]]
